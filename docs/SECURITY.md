# 安全策略

## 项目状态

Lumo 尚未正式发版，也未经生产环境检验。当前没有「受支持版本」的概念：
安全修复只进 `main`，请以最新提交为准。首个正式版本发布后，本文件会补上版本支持矩阵。

## 报告漏洞

**请不要用公开 Issue 报告安全问题。**

请走 GitHub 的私有漏洞报告通道：仓库页面 → **Security** → **Report a vulnerability**。
该渠道只有维护者可见，可以在修复就绪前保持不公开。

报告里请尽量包含：

- 受影响的组件与版本（提交哈希最好）
- 复现步骤，或一个最小复现用例
- 影响面：能读到什么、能改什么、需要什么前置权限
- 如果已有修复思路，也欢迎一并给出

## 响应

这是一个个人维护的项目，没有值班轮转。维护者会尽力做到：

- 7 天内确认收到报告
- 30 天内给出评估结论与修复计划

修复发布后会在安全通告中致谢报告者（如你希望匿名，请在报告中说明）。

## 影响范围

以下属于安全问题，欢迎报告：

- 认证与会话：会话固定、CSRF 绕过、PAT scope 越权、登录限流绕过
- 权限：绕过 `<资源>:<动作>` 鉴权，或绕过 `_any` 的所有权约束
- 内容安全：绕过正文净化拿到 XSS；评论转义被绕过
- 附件：路径穿越、扩展名白名单与内容嗅探被绕过、SSRF
- 主题与插件包：zip 解压穿越（zip slip）、模板沙箱逃逸
- 凭据：加密存储的口令字段以明文形式回传或泄漏
- SQL 注入、服务端模板注入、敏感信息写入日志

以下**不**属于安全问题：

- 需要管理员权限才能触发的行为——管理员本就能改站点的一切
- `content:unsafe_html` 权限允许的原始 HTML 直通：这是显式设计，该权限默认只给管理员
- 自建环境的错误配置，例如 HTTPS 下把 `secureCookies` 设成 `false`
- 缺少某项加固响应头，但没有可演示的实际影响
- 对公开接口的拒绝服务测试报告（限流之外的压测结果）

## 部署方须自行负责的事

- 数据库口令只走 `LUMO_DATABASE_DSN` 环境变量，不要写进配置文件
- 生产环境必须启用 HTTPS 并把 `server.secureCookies` 设为 `true`
- `server.trustedProxies` 默认为空（不信任任何代理）。只有在确实有反向代理时才填，
  填错会让 `X-Forwarded-For` 可被伪造，进而绕过按 IP 的限流
- `data/secret.key` 是主密钥，泄漏等于泄漏全部加密存储的凭据；请纳入备份与访问控制
